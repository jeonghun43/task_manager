# Constitution — Visual Task Manager

이 프로젝트의 모든 spec / plan / task는 아래 원칙을 위반할 수 없다.
충돌이 발생하면 이 문서가 우선한다.

## I. 시각적 구조가 곧 기능이다
"큰 과업 → 작은 과업" 계층은 데이터 모델의 부산물이 아니라 제품의 핵심이다.
어떤 화면에서든 지금 보고 있는 작은 과업이 **어느 큰 과업에 속하는지** 한눈에 보여야 한다.

## II. 하나의 데이터, 네 개의 시선
과업별 / 상태별 / 마감기한별 / 캘린더는 서로 다른 데이터가 아니라
**같은 데이터의 네 가지 투영(projection)** 이다.
한 뷰에서 바꾼 내용은 즉시 나머지 세 뷰에 반영된다.
뷰 전용 필드를 만들지 않는다.

## III. 로컬 우선, 서버 준비
1차 목표는 단일 사용자가 로그인 없이 즉시 쓰는 것이다.
단, 모든 영속화는 `StorageAdapter` 인터페이스를 통해서만 일어난다.
컴포넌트나 스토어가 `localStorage`를 직접 호출하면 위반이다.
(→ 향후 Supabase 어댑터 교체 시 UI 코드가 바뀌지 않아야 한다.)

## IV. 입력 비용 최소화
할 일 추가는 항상 **한 번의 클릭 + 제목 입력 + Enter** 로 끝난다.
마감일, 상태, 우선순위는 전부 선택 사항이며, 나중에 채울 수 있다.
필수 입력 필드는 제목뿐이다.

## V. 어떤 화면에서든 쓸 수 있다
모바일(≥360px)과 데스크톱(≥1280px)에서 모두 동작한다.
"데스크톱에서만 되는 기능"을 만들지 않는다.
드래그로 하는 모든 조작에는 반드시 대체 수단(메뉴/버튼)이 있어야 한다.

## VI. 데이터는 사용자의 것이다
언제든 전체 데이터를 JSON으로 내보내고 되돌릴 수 있어야 한다.
파괴적 동작(삭제)은 되돌리기 또는 확인 절차 없이 실행되지 않는다.
